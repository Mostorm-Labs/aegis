# Aegis v0.2.0-beta.4

Status: **Prerelease candidate**

```yaml
release_tag: v0.2.0-beta.4
channel: prerelease
```

## What beta.4 is

Beta.4 stabilizes the completion target after P31. It preserves failure-mode-first verification and independent Gate review while stopping Gate review from continuously expanding blocking completion requirements after implementation has started.

## Changes since beta.3

- Adds the **Gate Closure Stability Principle**: once P31 authorizes implementation, the blocking completion target is frozen.
- Upgrades P20 so important requirements map through failure modes, existing independent coverage, residual proof gaps, exact execution methods, and blocking versus corroborative evidence before implementation.
- Adds a mandatory P31 `EXECUTION_CLOSURE_CONTRACT` with required/forbidden changes, required tests, hosted verification, blocking/corroborative evidence, terminal success, explicit terminal blockers, and `continue_until_terminal_state: true`.
- Changes P32 so the executor continues through the complete frozen closure contract rather than returning at ordinary intermediate checkpoints.
- Adds `P33_REPETITION_GUARD`; Verification Design omissions route to P20 and Task Package omissions route to P31 instead of extending P33 indefinitely.
- Changes P34 to perform Frozen Requirement Audit, Frozen Evidence Audit, and Repository Reality Audit.
- Requires a late new blocking finding to identify a real uncovered high-impact failure mode, why frozen evidence did not cover it, and why severity justifies overriding closure stability.
- Makes redundant evidence, confidence improvements, diagnostics, auditability, observability, and hardening non-blocking for the current Gate when they add no unique high-impact detection value.
- Adds the **Anti-Proof-Recursion Rule** so evidence-for-evidence becomes blocking only when the evidence mechanism is itself a material undetected-failure source, lacks independent validation, and could materially affect the Gate decision.
- Restores assurance proportionality: Standard is the default for most ordinary feature/bugfix/module work; Full requires explicit risk justification.
- Keeps exact-source, clean-checkout, materialized-evidence, provenance, and independent-oracle controls available under Full or whenever the frozen Verification Contract genuinely requires them.

## Behavioral effect

The intended normal flow is now:

```text
P20 Verification closure
        ↓
P31 frozen Execution Closure Contract
        ↓
P32 execute to terminal state
        ↓
P34
  ├─ frozen obligations satisfied → PASS / PASS_WITH_FINDINGS
  └─ real uncovered high-impact defect → BLOCK / P35
```

P34 may still discover and block a real correctness, safety, security, compatibility, data-integrity, or release-critical defect. Closure stability prevents arbitrary finish-line movement; it does not weaken real defect detection.

## Compatibility

This is a behavioral tightening within the v0.2 lifecycle, not a Project State schema break. Existing global status/defect enums remain compatible. P35 adds late-finding routing labels such as `VERIFICATION_DESIGN_DEFECT`, `TASK_PACKAGE_DEFECT`, and `NON_BLOCKING_HARDENING` without requiring a global enum migration.

Existing P31 packages created under earlier versions remain readable, but active/incomplete work should regenerate or explicitly reconcile its completion contract before relying on beta.4's frozen-closure behavior.

## Verification

Beta.4 adds seven regression scenarios:

- stable closure after complete P20/P31;
- redundant evidence request stays non-blocking;
- real late high-impact uncovered defect still blocks;
- incomplete P31 package returns to P20/P31 before coding;
- repeated P33 package patching routes to the earlier defective layer;
- Standard profile does not require an evidence-only descendant by default;
- Full profile retains strict evidence controls when justified.

The release workflow revalidates Project State, deterministic Skillset generation, distribution contracts, routing, installed-platform state, generated Skill structure, protected eval corpus, repository regressions, exact-nine Plugin materialization, and release asset digests before publication.

## Upgrade / rollback

Use a whole-catalog Plugin transition or the published beta.4 Installation Kit. For reproducible rollback, use immutable `v0.2.0-beta.3` or an earlier published boundary.
